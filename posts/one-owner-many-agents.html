One Owner, Many Agents

Notes on the future of organizations: what happens to the org chart when one person, working with agents, can cover product, modeling and engineering?

TL;DR
  • Functional teams were built because implementation hours were scarce. Handoffs were the price we paid.
  • With agents, one owner can run a scoped project end to end. Context stays inside one loop instead of leaking at each handoff.
  • Large products get reorganized into owner-led slices that sit on a thin shared platform.
  • People coordinate through contracts and written decisions, not relays. Agents share a small, curated context layer.

For most of the history of software, the org chart has been a workaround for one hard constraint. Nobody can hold the whole stack in their head and also have the hours to build it. So we split work by function (product, algorithms, frontend, backend) and paid for that split with handoffs.

Agents loosen that constraint. If one person can direct agents that write the training code, the API and the UI, the basic unit of organization shifts from the function to the owner. This post sketches what that looks like, why it works (mostly: context), and what has to change around it. Treat it as a set of working hypotheses, not a report.

01The old shape: built for handoffs

Picture a typical ML product team: one PM, a designer, three algorithm engineers, one frontend engineer and one backend engineer. The PM talks to users and writes a spec. The algorithm engineers turn the spec into experiments. Backend wraps the model in an API, and frontend ships the UI. Every arrow in that pipeline is a translation, and every translation loses something.

Brooks pointed out the cost fifty years ago: n people have n(n−1)/2 potential communication channels (Brooks, 1975). Seven people already have 21. Much of a PM's week goes into keeping those channels in sync, through standups, spec reviews and "quick syncs."

The ratio of many algorithm engineers to one PM made sense when experiments were expensive: a PM's judgement was cheap compared with the engineering hours needed to test it. That ratio is flipping. When agents run the experiments and write the glue code, implementation hours stop being the bottleneck. The bottleneck becomes judgement: what to build, and whether it's good.

02The new shape: one owner, many agents

The alternative that's emerging: one person owns a project end to end. The owner acts as PM, algorithm engineer and full-stack engineer. That isn't because they're an expert at everything. Agents do most of the execution in each role, and the owner supplies direction, taste and review.

This is already partly visible. Anthropic describes data scientists with little JavaScript experience building full React apps to visualize model performance, and non-engineering teams building their own tools (Anthropic, 2025a). Amazon's single-threaded owner, one leader focused on one thing (Bryar & Carr, 2021), is being pushed down from the leadership level to the individual contributor.

The scarce resource is no longer implementation hours. It's judgement, and judgement doesn't survive a handoff well.

03Why context flows better

The main argument for the owner model isn't speed. It's context fidelity. Figure 2 is a cartoon of the difference.

  • No translation layer. The person who heard the user is the person who picks the loss function. A nuance like "users tolerate latency here, but hate confident wrong answers" doesn't have to survive a spec.
  • Decisions and implementation share a loop. When an experiment surprises you, the product plan can change within the hour, with no re-prioritization meeting.
  • Agents get better briefs. Anthropic found that subagents given vague task descriptions duplicated each other's work. The fix was a clear objective, an output format and explicit boundaries (Anthropic, 2025b). The person best placed to write that brief is the one holding the intent.

You can read this as Conway's law run in reverse. If systems mirror the communication structure of the teams that build them (Conway, 1968), a product built inside one loop has fewer seams for errors to leak through.

04Reorganizing a large product

One person can't own a search engine. Large products still need many people, so the real question is where to cut. My answer: cut by outcome, not by function.

  • Slices. Each slice (search ranking, recommendations, checkout, onboarding) gets one owner, a fleet of agents, and one metric the owner is accountable for. This is close to the stream-aligned team in Team Topologies (Skelton & Pais, 2019), shrunk down to one person.
  • A thin platform. Shared infrastructure, data, eval harnesses and the design system. The platform's customers now include agents, which means good docs, stable APIs and fast sandboxes matter more than ever.
  • Fewer managers who route work, more who review it. Managers spend less time routing work and more time reviewing quality, pairing owners and setting the bar.
  • Seams are contracts. Wherever two slices meet, the interface is explicit: an API schema, an event format, a shared metric definition.

05How people should work together

When each person owns more, people coordinate less often, but each coordination point matters more. A few norms seem to help:

  • Contracts over meetings. Agree on interfaces and metrics in writing, then work independently.
  • Write decisions down. A short decision log (what we chose, why, and what we rejected) can be read by colleagues and by agents.
  • Review, don't relay. People add value by reviewing each other's work, not by carrying messages between other people.
  • Demo early, async. A two-minute recorded demo beats a status meeting.
  • Pair at the seams. When two slices have to change together, the two owners pair for a day instead of coordinating for a week.

06What agents need to share

There's a tension here. Cognition argues that agents should share full context and full traces, because "actions carry implicit decisions," and decisions made with partial context tend to conflict (Yan, 2025). Anthropic, meanwhile, treats context as a finite resource to be curated down to the smallest high-signal set (Anthropic, 2025c). One way to reconcile the two: within a slice, share everything; across slices, share a small, distilled layer.

In practice, the six slots break down like this:

  • Intent: the goal, the non-goals, and who the user is. Without it, agents optimize the wrong thing very efficiently.
  • Decisions: what was decided and why, including the alternatives that were rejected, so nobody has to reopen them.
  • Contracts: API schemas, event formats, metric definitions. This is the only part another slice is allowed to depend on.
  • Evals: the shared definition of "good." If two slices measure quality differently, they will drift apart.
  • Conventions: coding style and repo rules, often written in a file agents read first (e.g. CLAUDE.md).
  • Memory: what was tried and didn't work. It's the cheapest way to stop an agent from repeating someone else's dead end.

07What could go wrong

  • A bus factor of one. If the owner disappears, the context goes with them. Mitigations: the decision log, and a buddy owner who reviews the slice every week.
  • Breadth without depth. An owner can ship a model they don't really understand. Keep deep experts as a shared review resource, not as a stage in the pipeline.
  • Burnout. Owning everything is heavy. Scope slices so one person can actually carry them, and split a slice before it breaks its owner.
  • Drift across slices. Shared evals and the design system are the guardrails. Invest in them first.

The org chart is starting to look like a software architecture. Owners are services, contracts are APIs, and the shared context layer is the database. That may not be a coincidence: we're finally organizing people the way we learned to organize code. I'd like to revisit these notes in a year and see which of them held up.
