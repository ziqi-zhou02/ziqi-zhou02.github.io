One Owner, Many Agents

Notes on how organizations change when one person, working with agents, can cover product, modeling and engineering.

TL;DR
  • Functional teams exist because implementation time used to be scarce, and handoffs were the cost of that arrangement.
  • With agents, one owner can run a scoped project end to end, so context stays in one loop instead of leaking at each handoff.
  • Large products can be split into slices that each have one owner, built on a thin shared platform.
  • People coordinate through contracts and written decisions, and agents work from a small shared context layer.

For most of the history of software, the org chart has worked around one constraint. Nobody could hold the whole stack in their head and also have the hours to build it, so we split the work by function into product, algorithms, frontend and backend, and accepted handoffs as the cost.

Agents relax that constraint. If one person can direct agents that write the training code, the API and the UI, the natural unit of organization moves from the function to the owner. In this post I sketch what that looks like, why I think it works, and what has to change around it. These are working hypotheses rather than findings.

01Functional teams were built around handoffs

A typical ML product team has one PM, a designer, three algorithm engineers, a frontend engineer and a backend engineer. The PM talks to users and writes a spec, the algorithm engineers turn it into experiments, backend wraps the model in an API, and frontend ships the UI. Each step in that pipeline is a translation, and each translation drops some detail.

Brooks described the cost fifty years ago. A team of n people has n(n−1)/2 possible communication channels (Brooks, 1975), so seven people already have 21. A good part of a PM's week goes into keeping those channels in sync through standups, spec reviews and quick check-ins.

The ratio of many engineers to one PM made sense when experiments were expensive. A PM's judgement cost little compared with the engineering time needed to test it. That ratio is now flipping. When agents run experiments and write glue code, implementation time stops being the bottleneck, and judgement about what to build and whether it is good becomes the scarce input.

02One owner can now run a whole project

The alternative is to give one person ownership of a project from end to end. That person acts as PM, algorithm engineer and full-stack engineer. They are not an expert in all of these roles. Agents do most of the execution in each one, and the owner provides direction, taste and review.

Parts of this are already visible. Anthropic describes data scientists with little JavaScript experience building full React apps to visualize model performance, and non-engineering teams building their own internal tools (Anthropic, 2025a). Amazon's idea of a single-threaded owner, one leader focused on one thing (Bryar & Carr, 2021), is moving down from senior leaders to individual contributors.

The scarce resource is shifting from implementation hours to judgement, and judgement does not survive a handoff very well.

03Context survives better inside one loop

The strongest argument for the owner model is about context more than speed. Figure 2 is a cartoon of the difference.

  • No translation layer. The person who talked to the user also chooses the loss function. A detail like "users tolerate latency on this page but hate confident wrong answers" never has to survive a spec.
  • Decisions and implementation share a loop. When an experiment surprises the owner, the product plan can change within the hour without a reprioritization meeting.
  • Agents get better briefs. In Anthropic's multi-agent research system, subagents given vague task descriptions duplicated each other's work, and clear objectives, output formats and boundaries fixed the problem (Anthropic, 2025b). The person holding the intent is the one best placed to write those briefs.

This is Conway's law in reverse. If systems mirror the communication structure of the teams that build them (Conway, 1968), a product built inside one loop has fewer seams for errors to leak through.

04Large products split into slices by outcome

One person cannot own a search engine, so large products still need many people. The real design question is where to draw the lines, and I think the answer is to cut by outcome rather than by function.

  • Slices. Each slice, such as search ranking, recommendations, checkout or onboarding, has one owner, a set of agents and one metric the owner answers for. This is close to the stream-aligned team in Team Topologies (Skelton & Pais, 2019), shrunk to a single person.
  • A thin platform. Infrastructure, data, eval harnesses and the design system are shared. Agents are now among the platform's main users, so clear docs, stable APIs and fast sandboxes matter more than before.
  • Managers who review. Managers spend less time routing work and more time reviewing quality, pairing owners and setting the bar.
  • Contracts at the seams. Where two slices meet, the interface is written down as an API schema, an event format or a shared metric definition.

05People coordinate through contracts and written decisions

When each person owns more, people coordinate less often, but each point of coordination carries more weight. A few norms seem to help.

  • Contracts over meetings. Agree on interfaces and metrics in writing, then work independently.
  • Written decisions. A short decision log that records what was chosen, why, and what was rejected can be read by colleagues and by agents.
  • Review instead of relay. People add value by reviewing each other's work, and very little by passing messages along.
  • Early async demos. A two-minute recorded demo usually replaces a status meeting.
  • Pairing at the seams. When two slices have to change together, the two owners pair for a day instead of coordinating for a week.

06Agents share a small, curated context layer

There is a tension in the current advice. Cognition argues that agents should share full context and full traces, because actions carry implicit decisions and decisions made with partial context tend to conflict (Yan, 2025). Anthropic treats context as a finite resource that should be curated down to the smallest high-signal set (Anthropic, 2025c). I think both are right at different scales. Within a slice agents should share everything, and across slices they should share a small, distilled layer.

The layer in Figure 4 has six parts.

  • Intent. The goal, the non-goals and the intended user. Without it, agents optimize the wrong thing very efficiently.
  • Decisions. What was decided and why, including rejected alternatives, so nobody has to reopen them.
  • Contracts. API schemas, event formats and metric definitions. This is the only part another slice should depend on.
  • Evals. The shared definition of good. Slices that measure quality differently drift apart.
  • Conventions. Coding style and repo rules, often kept in a file that agents read first, such as CLAUDE.md.
  • Memory. A record of what was tried and failed, which is the cheapest way to stop an agent from repeating someone else's dead end.

07The model has real failure modes

  • One person as a single point of failure. If the owner leaves, the context leaves with them. A decision log and a buddy owner who reviews the slice each week reduce the risk.
  • Breadth without depth. An owner can ship a model they do not fully understand. Deep experts are still needed, as shared reviewers rather than as a step in the pipeline.
  • Burnout. Owning everything is heavy. Slices should be scoped so that one person can carry them, and split before they break their owner.
  • Drift across slices. Shared evals and the design system act as guardrails, and they are worth investing in first.

The org chart is starting to resemble a software architecture, with owners as services, contracts as APIs and the shared context layer as the database. I don't think that is a coincidence, since we are organizing people in a way we already learned to organize code. I plan to revisit these notes in a year and see which of them held up.
